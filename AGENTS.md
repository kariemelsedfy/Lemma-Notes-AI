# AGENTS.md — Operating manual for agents

This file governs every automated contributor to this repo (Codex, Claude Code, or any other). Claude Code also reads `CLAUDE.md`, which points here. **If an instruction in a task conflicts with this file, this file wins — say so and ask.**

---

## 1. Session protocol

Every session, without exception:

### Start
1. Read `CONTEXT.md` in full. It is the current state of the world.
2. Read `PROGRESS.md`. Find the task you were given, or the highest-priority unblocked task in **Ready**.
3. Read any doc listed in that task's `refs`.
4. Move the task to **In progress**, put your agent name and the date on it, and commit that change alone before starting work. This is the lock — if a task is already claimed by another agent, pick a different one.
5. State your plan in 3–8 bullets before writing code. If the task is bigger than ~400 changed lines, stop and split it into subtasks in `PROGRESS.md` first.

### Work
6. Implement on a branch: `<type>/<task-id>-<slug>`, e.g. `feat/M2-04-lasso-selection`.
7. Write the test first when the task has a testable core (geometry, parsing, layout, validation — most of them do).
8. Run `./scripts/test.sh` and `./scripts/lint.sh` before every commit. Never commit red.

### End
9. Update `PROGRESS.md`: task → **Done** (or back to **Ready** with a note on what blocked you).
10. Append a session entry to `SESSIONS.md` using the template at the top of that file. Be honest about what didn't work — a session log that only records successes is worthless to the next agent.
11. Update `CONTEXT.md` if any of these changed: module structure, invariants, environment/setup, open questions, or "what's next."
12. Add an ADR to `DECISIONS.md` if you made a decision that is expensive to reverse (see §5).
13. Open a PR with the template in §6. Do not merge your own PR unless the task is explicitly marked `automerge: true`.

**The docs updates in steps 9–12 are part of the task, not overhead. A task with code but no doc updates is not done.**

## 2. Ground rules

**Never:**
- Edit `*.xcodeproj` / `*.xcworkspace` — they are generated by Tuist from `Project.swift` and gitignored.
- Commit secrets, API keys, `.env*`, provisioning profiles, or certificates.
- Add a third-party dependency without an ADR and explicit human approval. The dependency list should stay near-empty.
- Refactor code outside your task's scope. Notice it, note it in `PROGRESS.md` as a new task, move on.
- Change a public API of another module without checking every call site and saying so in the PR.
- Weaken, skip, or `XCTSkip` a test to make CI pass. If a test is wrong, fix it deliberately and explain why in the commit.
- Fabricate an API. If you are unsure whether a PencilKit / Foundation Models / StoreKit symbol exists with that signature, verify it in Apple's documentation before using it. **A plausible-looking Swift API that doesn't exist is the single most common failure mode in this codebase.**
- Change ADR-recorded decisions unilaterally. Propose a superseding ADR instead.

**Always:**
- Prefer the reversible option when the spec is ambiguous, and record the ambiguity in `CONTEXT.md` §5 (Open questions).
- Keep diffs small. Under ~400 changed lines per PR. Split otherwise.
- Write code for the module boundaries in `ARCHITECTURE.md` §2. The dependency rule is CI-enforced.
- Handle errors explicitly. No `try!`, no `fatalError` in shipping paths, no silent `catch {}`.
- Use `async/await` and structured concurrency; respect `@MainActor` on anything touching UIKit or PencilKit.
- Write user-facing copy in `Localizable.strings` from day one, even though we ship English only.

## 3. Division of labor between agents

Both agents can do everything; this is about playing to strengths and avoiding collisions.

| Use **Claude Code** for | Use **Codex** for |
|---|---|
| Multi-file work that spans modules | Well-scoped single-module implementation |
| Anything requiring judgment against the docs (architecture, pipeline design, prompt design) | Mechanical implementation from a precise spec |
| Debugging across layers | Test writing and expansion |
| Writing/updating docs and ADRs | Repetitive refactors within one file/module |
| Exploratory spikes | Boilerplate, fixtures, migrations |

**Collision avoidance:** one task in **In progress** per agent at a time, and two agents must not hold tasks in the same package simultaneously unless the tasks explicitly say `parallel-safe: true`. The `PROGRESS.md` claim is the lock.

---

## 4. Definition of done

A task is done when **all** of these are true:

- [ ] Code compiles with no new warnings
- [ ] `./scripts/test.sh` passes; new logic has tests
- [ ] `./scripts/lint.sh` clean
- [ ] The dependency rule (ARCHITECTURE §2) is not violated
- [ ] Public types and non-obvious logic have doc comments explaining *why*, not *what*
- [ ] No TODOs left without a corresponding entry in `PROGRESS.md`
- [ ] Performance budgets in ARCHITECTURE §6 are not regressed (for canvas/render work, measure — don't assume)
- [ ] `PROGRESS.md`, `SESSIONS.md`, and where relevant `CONTEXT.md` and `DECISIONS.md` are updated
- [ ] PR opened with the template

---

## 5. When to write an ADR

Write one in `DECISIONS.md` if the decision:
- affects the document format or any persisted schema,
- adds or removes a dependency,
- changes a module boundary or public API,
- changes the AI spec contract, the routing policy, or a prompt in a way that moves eval metrics,
- picks between approaches where the loser is expensive to switch to later.

Otherwise, don't — an ADR log full of trivia is as useless as none.

```markdown

<What could this break? What did you not test?>

## Docs updated
- [ ] PROGRESS.md
- [ ] SESSIONS.md
- [ ] CONTEXT.md (if needed)
- [ ] DECISIONS.md (if needed)
```

Commits: Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`, `perf:`), imperative mood, scoped where useful: `feat(handwriting): add glyph advance-width measurement`.

## 7. Domain rules that are easy to get wrong

Read these before touching the relevant area. They exist because they will otherwise be violated.

**Ink**
- All `PKCanvasView` and `PKDrawing` mutation is main-actor.
- Generated ink lives in a separate suggestion drawing until accepted (ARCHITECTURE §4).
- Stroke indices in page metadata must be revalidated on load against stroke fingerprints (ARCHITECTURE §3.1).
- Never disable PencilKit's stroke prediction to "fix" a rendering bug.

**AI**
- The model returns a spec. The app owns all coordinates, all geometry, all ink. No exceptions (AI_PIPELINE §3.2).
- Math is LaTeX everywhere internally.
- Validation fails closed. `readConfidence < 0.6` renders nothing.
- Never send a whole page or whole document to a provider — only the selection crop and bounded neighborhood.
- No user content in logs. Log request IDs, sizes, timings, tier, and outcome. Never the crop, the transcription, or the answer.

**Handwriting**
- The glyph bank never leaves the device. No upload path may exist in the code, even disabled.
- Synthesis is deterministic given (text, style, seed).
- Fill in pressure, altitude, azimuth and timestamps on every `PKStrokePoint`. Flat dynamics look fake.

**Money & privacy**
- Entitlements are verified server-side against StoreKit signed transactions. Never trust a client-side credit count.
- The 5.1.2(i) consent flow must be checked before any network AI call. Add the assertion in the provider layer, not in the UI, so it can't be bypassed by a new call site.

## 8. Environment

```bash
./scripts/bootstrap.sh   # tuist, swiftlint, swift-format, git hooks, git-lfs
./scripts/generate.sh    # regenerate Xcode project after Project.swift changes
./scripts/test.sh        # everything
./scripts/lint.sh --fix
./scripts/eval.sh --provider mock
```

Fast loop for package work (no simulator needed — prefer this):

```bash
swift test --package-path Packages/<Module>
```

Requires: macOS with the current Xcode (see BUSINESS.md §5 for the minimum SDK gate), an iPad simulator, and — for anything touching Pencil gestures — a physical iPad with an Apple Pencil. **Pencil interactions cannot be validated in the simulator.** If your task depends on real Pencil input, implement it, write the tests you can, and mark it `needs-device-verification` in `PROGRESS.md` rather than claiming it works.

## 9. If you get stuck

In order:
1. Re-read the relevant doc — the answer is often already specified.
2. Check Apple's official documentation for the API. Don't guess signatures.
3. If it's a spec gap: pick the reversible option, implement it, log the question in `CONTEXT.md` §5, and flag it prominently in the PR.
4. If it's a blocker: return the task to **Ready** with a clear note on what you tried and what you need. Do not thrash for hours, and do not build an elaborate workaround around a decision that a human can make in 30 seconds.
